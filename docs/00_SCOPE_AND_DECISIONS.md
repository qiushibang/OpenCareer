# 00 — 项目范围与已确认决策

## 1. 产品愿景

构建一个面向中国 AI/互联网求职者的统一求职 Agent，覆盖“发现机会 → 理解 JD →
匹配经历 → 生成材料 → 跟踪申请 → 模拟面试 → 复盘提升”。

## 2. 当前产品的一句话定义

> 基于 OpenWorker 的本地优先求职 Agent，以可追溯岗位和已确认简历事实为基础，
> 在同一 Conversation 体验中完成岗位发现、申请准备和面试训练。

## 3. 已确定技术决策

### D-001：OpenWorker-first

OpenWorker 是主仓库、Agent Harness 和桌面应用基线。Career 能力不在未来才接入，而是从开发第一天就通过 Persona、Skill 和 MCP 贯通。

### D-002：单仓库优先

个人开发阶段使用一个 OpenWorker Fork。Career 领域代码放在独立目录，但与 OpenWorker 一起运行、测试和演示。后期确有部署需求再拆仓库或服务。

### D-003：Conversation-first

标准 Conversation 是 Agent 任务、审批、语音输入和模拟面试的唯一主界面。岗位雷达、
求职档案等确定性数据使用专用页面，但不复制 Agent Loop 或 Conversation 状态。

### D-004：官方来源优先

数据优先级：

1. 用户粘贴的 JD。
2. 官方公开 API。
3. 官方页面公开 JSON/XHR。
4. 官方 HTML、JSON-LD、内嵌数据。
5. Playwright 动态渲染。
6. 第三方聚合只作为线索，不作为事实唯一来源。

### D-005：轻量本地运行

MVP 默认 SQLite、本地文件、单进程或轻量调度。先在个人 Mac 完整跑通，再部署低配置云服务器。

### D-006：不依赖 LLM 做常规爬虫

页面请求、解析、字段映射、哈希、去重、状态变化使用确定性代码。仅在手动 JD 或难以规则化的文本结构化时允许模型辅助。

### D-007：事实和证据优先

岗位结论必须能追溯到官方 URL，简历结论必须能追溯到用户确认的事实。匹配、材料和
面试问题都不得把模型推断伪装成用户经历。

### D-008：语音是 Conversation 输入能力

语音输入属于 Composer，不属于模拟面试专用状态。浏览器使用豆包 ASR，桌面端使用
本地 Whisper；识别结果只进入草稿，不自动发送。

### D-009：模块化单体

OpenWorker 核心与 Career 领域通过 MCP 分隔。当前保持本地 SQLite 和单仓库，不因
未来云部署预先引入微服务、消息队列或向量数据库。

## 4. 已实现范围

- Career Persona、Skills、可信工作区 MCP。
- 手动 JD、官方招聘源、岗位版本和变化事件。
- 岗位雷达、筛选、详情、收藏和申请进度。
- 多简历 Career Vault、事实确认、离线 OCR 和安全删除。
- 岗位/简历证据匹配和申请准备包。
- 基于证据逐条确认的定制简历 DOCX/PDF。
- JD/简历驱动的多轮模拟面试、复盘和历史记录。
- 所有 Agent Conversation 的文字和语音输入。

## 5. 当前明确排除

- 科研和学术资料。
- 申博、申硕、夏令营。
- 考公。
- 海外公司和海外岗位。
- 自动批量投递。
- 招聘网站账号自动化。
- 验证码识别和反爬绕过。
- 企业端招聘服务。
- 视频表情或诚信判断。

## 6. 招聘源范围

招聘源按公开数据可用性和维护成本准入，不以公司数量作为完成标准。当前覆盖和禁用
原因以 `13_SOURCE_COVERAGE_MATRIX.md` 与 `source-notes/` 为准。

任何来源如果需要登录、验证码、复用私有签名或绕过访问控制，立即降级为手动 JD，
不得为了覆盖率降低合规门槛。

## 7. 产品原则

- 来源可追溯比岗位数量更重要。
- 正确的 3 家 Adapter 比不稳定的 30 家更有价值。
- 用户始终能通过手动 JD 完成核心任务。
- Agent 不编造经历或岗位信息。
- 先做端到端闭环，再做漂亮页面。
- 明确的设备级验收不能用 mock 或合成数据冒充。
