# AI 简历诊断与面试准备对话设计

## 目标

将岗位详情中的“岗位与简历证据匹配”从用户可见功能降级为旧流程的内部
兼容能力。新的主流程由 Career Agent 直接读取一份目标岗位和一份已确认简历，
使用模型完成诊断、事实追问、逐段改写建议和针对性面试准备。

成功标准：

1. 用户在岗位详情点击“AI 分析与改简历”，选择一份已确认简历后进入
   Career Conversation。
2. 系统自动发送首轮诊断请求，不要求用户再次点击发送。
3. 新流程不调用脚本匹配，不创建匹配快照，不展示证据矩阵、匹配数量、排序或
   推荐简历。
4. 模型只使用当前岗位、所选简历的已确认事实和用户在对话中补充确认的事实。
5. 输出直接服务于简历修改和面试准备，不创建侧栏报告、申请准备包、定制简历
   草稿、DOCX 或 PDF。

## 已确认决策

### 入口

采用“极简选择后进入 Career Agent”：

1. 岗位详情将“匹配简历”改为“AI 分析与改简历”。
2. 点击后只显示未删除且至少包含一个已确认章节的简历。
3. 用户单选一份简历并确认。
4. 前端创建新的 Career Conversation，并自动发送诊断请求。

不采用直接猜测默认简历，因为选错简历会污染整轮分析。不采用轻量诊断抽屉，
因为它会形成主对话之外的第二套分析界面。

### 分析引擎

所有岗位与简历分析均由 AI 完成。新流程明确禁止：

- 调用 `createCareerJobMatches` 或岗位匹配 MCP 工具。
- 创建或读取 `job_resume_matches` 作为诊断输入。
- 使用关键词命中、证据计数、权重公式、简历排序或脚本评分。
- 将旧证据矩阵包装成模型分析结果。

现有确定性匹配服务和快照本轮不删除，仅作为模拟面试等旧流程的兼容依赖保留。
它们不得参与新的简历诊断流程。彻底移除旧匹配依赖属于后续独立规格。

## 用户流程

```text
岗位详情
→ 点击“AI 分析与改简历”
→ 单选一份已确认简历
→ 创建 Career Conversation
→ 自动发送 job_id + resume_id
→ Agent 读取完整 JD 和该简历的已确认、脱敏事实
→ AI 输出首轮诊断与事实追问
→ 用户补充或确认事实
→ AI 输出逐段修改建议、可复制改写稿和面试准备
```

对话是唯一分析工作区。岗位页不显示分析摘要、证据矩阵、匹配状态或生成结果。

## AI 分析策略

### 优先级

模型按以下顺序分析：

1. 项目经历。
2. 实习与工作经历。
3. 基础能力与技能。
4. 教育经历。

教育经历只检查 JD 明确提出的学历、专业、毕业时间等要求，不作为泛化推荐或
简历优劣判断的主要依据。

### 首轮诊断

首轮响应固定包含：

1. 项目与实习证据。
2. 基础能力覆盖。
3. JD 缺失项。
4. 需要用户补充的真实事实。

“缺失”只表示所选简历尚未体现，不表示用户不具备该能力。模型不得将缺失项
直接写入简历，必须先追问用户。

### 事实确认后的交付

用户在当前对话中明确陈述或肯定补充事实后，模型逐段输出：

- 操作标签：`保留`、`删除`、`补充`、`重写` 或 `加粗`。
- 原简历事实或用户本轮确认的事实来源。
- 修改理由及其对应的 JD 要求。
- 可复制的改写文本。

模型不生成整份文件，不覆盖 Career Vault 中的原简历，不确认结构化事实，也不
调用申请准备包、定制简历草稿或导出工具。

### 面试准备

面试准备与逐段改写结果同轮输出，并按当前简历中的每段相关项目或实习经历组织：

- 核心问题。
- 可能追问。
- 面试官验证的能力点。
- 当前简历尚未支撑该回答的事实。

问题必须与当前 JD 和所选简历相关，不生成通用面试题库。

## 数据与工具边界

### 启动载荷

前端只向 Conversation 发送不透明标识：

```text
job_id=<job id>
resume_id=<resume id>
```

载荷不得包含简历正文、联系方式、文件路径、上传 token 或匹配快照 ID。

### 岗位读取

Agent 继续通过现有 `get_job(job_id)` MCP 工具读取当前租户可见的完整岗位。
岗位不存在或不可见时停止分析并返回明确错误。

### 单份简历读取

新增只读 MCP 工具：

```text
get_confirmed_resume(resume_id)
```

该工具：

- 只返回当前 Principal 可见的指定简历。
- 只返回用户已确认的章节和结构化事实。
- 默认排除或遮罩手机号、邮箱、身份证、精确住址等敏感字段。
- 拒绝未确认、已删除、其他租户或不存在的简历。
- 不执行匹配、评分、排序、摘要生成或模型调用。

前端继续通过现有 `GET /v1/career/resumes` 读取选择摘要；Agent 可通过
`list_confirmed_resumes()` 查看安全摘要。两者都不能替代单份简历事实读取。

## 前端边界

### 岗位页启动器

现有 `CareerJobMatchPanel` 收敛为单一职责启动器：

- 打开简历选择弹层。
- 读取已确认简历摘要。
- 维护单选状态和加载/错误状态。
- 向 `App` 提交 `{ jobId, resumeId }`。

组件删除：

- 历史匹配读取和创建。
- 多简历选择与比较。
- 证据矩阵、推荐和 stale 展示。
- “生成申请准备包”入口。
- “生成定制简历建议”入口。
- `CareerTailoredResumePanel` 嵌入。

实施时可以同步把组件改名为表达真实职责的名称，但不得借机重构岗位页面其他
区域。

### Conversation 启动

`App` 负责：

1. 校验可信工作区。
2. 创建新的 Career Session。
3. 切换到标准 Conversation。
4. 排队一条仅包含 `job_id`、`resume_id` 和明确任务约束的首轮消息。
5. WebSocket 就绪后只发送一次。

该流程复用现有模拟面试的 queued-turn 思路，但使用独立状态，避免简历诊断与
面试首题相互覆盖。失败时不得遗留无标题、无内容的空会话。

## 错误处理

- 无已确认简历：留在选择弹层，提示前往“我的求职档案”导入并确认。
- 简历读取失败：显示服务端安全错误，不回退到未确认文本。
- 岗位或简历不可见：停止分析，不泄露资源是否属于其他租户。
- 无可信工作区：创建 Conversation 前失败并提示用户选择可信工作区。
- WebSocket 连接失败：保留可重试状态，不重复发送诊断消息。
- Agent 工具失败：在 Conversation 中给出可理解错误，不调用旧脚本匹配兜底。

## 隐私与事实边界

- HTTP、WebSocket、Origin、静态 token/JWT 和租户隔离规则保持不变。
- 前端不持有简历正文，不把敏感联系方式写入 Prompt。
- Agent 不得根据职位要求推断用户拥有未确认的技能、成果、年限或数字。
- 用户在对话中补充的事实必须由用户明确陈述或肯定后才能用于本轮改写；这些事实
  不自动写回 Career Vault，也不能在后续会话中冒充已持久化事实。
- “加粗”是文本呈现建议，不修改 PDF，也不表示匹配结论。

## 本轮不做

- 不删除匹配数据库表、MatchService 或模拟面试的兼容调用。
- 不删除申请准备包和 PDF/DOCX 后端服务、API、数据库迁移或历史数据。
- 不生成新的侧栏、报告页、评分面板或匹配百分比。
- 不自动写回 Career Vault，不自动生成或下载任何文件。
- 不改变模拟面试入口、面试状态机或生产部署配置。

申请准备包、旧定制简历状态机及 PDF/DOCX 导出链路的彻底删除在下一份规格中
单独设计，包含历史数据兼容、API 下线和数据库迁移策略。

## TDD 与验收

实施必须遵循 RED → GREEN：

1. 前端测试先证明岗位详情只显示“AI 分析与改简历”，不再显示旧匹配、申请包和
   草稿入口。
2. 启动器测试证明只能选择一份已确认简历，并提交精确的 `jobId`、`resumeId`。
3. App 测试证明进入 Career Conversation 后自动且仅发送一次诊断请求。
4. Prompt 测试证明只包含不透明 ID 和任务约束，不包含简历正文、敏感信息或
   `snapshot_id`。
5. MCP 测试证明 `get_confirmed_resume` 只返回指定租户的已确认、脱敏事实。
6. Skill/Persona 测试证明新流程禁止调用匹配、申请包和导出工具，并包含已确认的
   分析优先级与输出结构。
7. 现有模拟面试聚焦回归继续通过，证明兼容匹配依赖未被破坏。
8. 在 `375×812` 和桌面视口验证选择弹层无横向溢出、控件遮挡或文字截断。
