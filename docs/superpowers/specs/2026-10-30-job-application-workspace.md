# OpenCareer 求职进度工作台：产品与改造方案

日期：2026-10-30（北京时间）。状态：**首版本地实现与验收**。表格、真实面试/面经、Excel导出及旧进度兼容已实现；使用与边界见[首版指南](../../25_APPLICATION_WORKSPACE.md)。看板、日历、自定义字段和外部连接仍属后续范围。本批不部署或修改生产服务。

## 1. 产品方向与证据

把岗位详情里的「我的申请进度」扩展为侧栏独立入口「求职进度」。工作台以可编辑表格为主，一行是一项具体岗位的一次申请流程；同公司不同岗位、城市、招聘批次都能分别管理。表格负责比较与推进，右侧详情负责完整职位描述、面试记录和面经。

调研整理了12条求职管理来源及3份官方导出资料，含作者自用分享、开源工具、模板推广与官方帮助，逐条标注读取边界，见[调研笔记](../../research/2026-10-30-job-application-tracking.md)。这是定性样本，不是普遍用户比例或效果证明。

- [牛客华墨的自用秋招记录分享](https://www.nowcoder.com/discuss/402585420964409344)分享了其自用记录模板并看重筛选；[PocketSWPU 的表格记录生成器](https://github.com/PocketSWPU/TableRecordGenerator)将减少重复输入作为动机。因此，加入记录时应直接带入岗位信息。
- [Zheyi-D 的个人飞书记录工具](https://github.com/Zheyi-D/job-tracker-extension)包含一面、二面、三面、人力面试；[安蓝笔记的模板发布简介](https://www.bilibili.com/video/BV1w14y1F7yT/)提到日历、职位描述和复盘。后者仅简介索引可读，未播放视频。这些启发我们把每场面试关联保存，而不是横向增加无穷多列。
- [一位模板作者关于忘记投出哪版简历的自述](https://www.reddit.com/r/notioncreations/comments/1rxwg14/i_made_a_notion_job_tracker_that_solves_an/)支持保留简历版本与下一步；该来源含付费推广，只采用其明确描述的痛点。

首版获得多维表格的主要便利：直接编辑、选择列、排序筛选、状态分组和关联详情。不复制飞书完整表格引擎，不依赖飞书账号，不做任意公式、多人协作或自动投递。

## 2. 页面与使用流程

侧栏增加「求职进度」，与「岗位雷达」「我的求职档案」并列。雷达继续负责发现岗位；求职档案保存简历和已确认经历；求职进度管理本人准备与实际投递。

雷达详情增加「加入求职进度」。点击后带入公司、岗位、地点、招聘类型、官网链接和当时的完整职位描述；默认是待准备，**加入管理或打开官网都不等于已经投递**。旧进度大表单后续收成一条摘要，例如「面试中 · 二面待反馈 · 打开进度」，避免岗位浏览页承担完整管理工作。此处与总表必须读写同一份申请数据。

表格顶栏为搜索、筛选、分组、显示列、新建申请、导出 Excel。公司和岗位固定在左侧，默认展示约10列：公司、岗位、地点、申请状态、当前阶段、投递日期、下一步、下次时间、岗位薪资、优先级。长职位描述、面经和详细备注不塞满行高，点击岗位打开侧栏详情。隐藏列不删除数据。

提供预设视图「全部申请」「准备投递」「面试中」「待跟进」「Offer」「已结束」。每个视图只保存条件和显示设置，不能复制成互相失联的多份表。表格能按公司、城市、类型、批次、阶段、日期和自定义标签筛选；首版标签可自填，额外自定义字段类型放后续阶段。

支持手动新增岗位雷达之外的机会，例如内推、邮件沟通或招聘平台岗位。无需先变成公共岗位或配置模型，手工管理与导出都能独立使用。

## 3. 字段和关联模型

| 字段组 | 首版字段 | 规则 |
|---|---|---|
| 岗位与来源 | 公司、岗位名、工作地点、招聘类型、招聘批次、部门/业务线、来源渠道、原始链接、职位描述副本 | 业务线未知允许空；同公司多岗位不合并。批次如2027秋招/日常实习，由用户填写或确认，不能从采集日期猜测。 |
| 流程 | 申请状态、当前阶段、投递日期、最近操作、优先级、标签 | 保留原状态语义；无回复不能自动判为未通过。状态更新时间不能冒充投递日期。 |
| 下一步 | 事项、计划时间、截止时间、完成状态 | 首页和表格可显示今日/逾期事项；首版不承诺关机后提醒，不默认群发消息。 |
| 薪资 | 岗位公布薪资、个人期望、实际Offer报价、币种、月薪/年薪/日薪、发薪月数、补充说明 | 公布范围与本人报价分开；未知、面议不当作0，不能由模型补出薪资或默默换算税后收入。 |
| 准备材料 | 投出简历版本、相关模拟面试、个人备注 | 关联既有档案和文件标识，保存名称/版本说明/摘要哈希；未经用户确认，不能声称这就是实际投出的文件。 |
| 面试与面经 | 任意轮次、面试类型、形式、时间、安排状态、结果、问题、回答要点、复盘、待补知识 | 每场单独记录，允许加面、HR面、改期、取消、待反馈；模拟面试与真实招聘面试明确区分。 |

**申请状态、当前阶段、面试结果分别回答不同问题。** 申请状态可沿用现有待准备/已投递/测评中/面试中/已获Offer/已接受/未通过/已撤回等含义；当前阶段显示简历筛选、笔试、业务一面、二面、终面、HR面或谈薪。一次面试另有「待安排/已约/已完成/已取消」与「待反馈/通过/未通过/未记录」。一面已完成不等于一面通过，也不意味着自动安排二面；只有用户明确记录的结果才推进状态。

建议的领域实体：

```text
公共岗位（可为空） ── 个人申请记录 ── 多场真实面试及逐场面经
                          │
                          ├─ 流程变更历史与下一步
                          ├─ 用户选定的简历版本
                          └─ 既有模拟面试（单独标记）
```

个人申请有独立编号，岗位链接只用于关联。保存加入时的职位描述副本及来源版本；官网后来改写、下线、爬虫更新或删除源，都不能覆盖用户面经、私有薪资、备注和当时的职位描述。重新应聘同一岗位可明确新建一次申请；重复点击加入时先定位已有记录，避免意外重复。

## 4. Excel 导出：首版必须交付

顶栏「导出 Excel」直接下载真正的 `.xlsx`，不要求飞书授权，也不上传到转换网站。菜单提供当前筛选、全部申请、勾选记录；**当前筛选包含所有分页**，绝不是只导出屏幕上几十行，更不能把公共岗位库全部混入私人投递记录。

工作簿建议含「申请总表」「面试记录」「职位描述与面经」「字段说明」。以申请编号、面试编号关联，既能直接读，也能另存或整理；导出日期采用北京时间并在说明中写清。职位描述和面经保留全文，不只导出页面摘要，原始链接保持可用。Excel用于可携带记录；不声称能够恢复所有视图、原简历附件或软件完整状态，完整备份仍沿用数据目录备份。

项目已使用 SheetJS（`xlsx`）读取表格，首版复用该依赖按需加载写出，无需再接外部表格服务。正式实现前验证所需写出能力，不把未支持的样式或冻结窗格当成既有能力。[官方写出说明](https://docs.sheetjs.com/docs/api/write-options/)

[Excel官方限制](https://support.microsoft.com/en-us/excel/excel-specifications-and-limits)为每格32767字符、253次换行。超长或多换行内容按申请编号、字段、段号分行保存，导出后应能逐段拼回全文，不能静默截断。职位描述、面经、备注均按文本单元格写出，不能把外部正文写入公式字段；用以 `= + - @` 开头的示例及含公式样式正文做写出/回读验收。[SheetJS单元格模型](https://docs.sheetjs.com/docs/csf/cell/)

导出按当前用户和明确的筛选取得一致性结果，保留数字、日期、中文、多行文本和空值。使用专门的个人申请导出数据接口与现有前端工作簿库，不依赖模型处理正文。大型结果应有进度和可取消状态；若超过安全上限，应明确提示缩小范围，不能悄悄漏行或导出部分却标为完整。

## 5. 对现有项目的最小改造

现有 `JobTrackingService`、`JobTrackingRepository` 只保存每岗收藏、单个申请状态、2000字备注及状态时间线；没有独立申请对象、面试轮次、薪资或投出简历关联，不能只加几个界面列就称为完整进度管理。

在 Career 领域模块增量增加申请记录、面试记录、流程事件三类持久化与服务，复用现有岗位、简历库、模拟面试、当前用户上下文和版本冲突检查。个人申请不放公共岗位快照，不重写Agent循环、权限引擎或调度。界面新增工作台，旧详情进度转为同一服务的轻量入口。

旧记录按明确的申请状态、投递记录一次性迁入，保留编号映射、备注、历史、收藏和时间出处。只有收藏且未进入流程的岗位不自动变成投递申请；仅有笔记的岗位可在用户加入时带入。迁移未知轮次保持未知，不能给旧「面试中」补造一面/二面或通过结果。旧版接口先保留兼容投影；同岗位存在多次申请时必须指向明确的当前记录或要求选择，不能把状态写给错误批次。

本地先以增量 SQLite 迁移和独立浏览器验收完成，迁移前备份，重复迁移幂等。设计保留 PostgreSQL 数据访问边界和既有用户隔离，后续上线再单独检查迁移与回滚；本方案阶段不改线上数据库。云端所有查询、修改与导出由服务器已有当前用户上下文决定归属，不能接受前端任意传入用户编号来切换记录。

第一版表格采用现有React组件及固定分页/服务端筛选，按数据量评估是否需要虚拟滚动；不为了个人管理一次引入完整协作表格套件。编辑失败保留草稿，后台岗位刷新不能冲掉正在写的备注。第一版无需模型即可用；后续通过已有工具注册提供读表、加入申请与记录面试的受限工具。只有用户明确要求才能写入私人进度，岗位正文和模型猜测不能作为修改指令。

## 6. 分期与验收

**第一期：可真正替代手工投递表。** 交付独立入口、雷达加入/手动新增、可编辑表格与筛选/排序/列设置、申请详情、下一步日期、任意轮次面试及面经、薪资区分、简历版本关联、`.xlsx`完整导出及旧记录迁移。先完成一条申请从加入到二面复盘再导出的闭环，再扩展批量操作。首期不依赖任何外部账号。

**第二期：多视图与低成本维护。** 增加按状态分组的看板、事项日历、少量类型明确的自定义字段、外部Excel导入与字段映射、Offer对比。AI可按真实记录总结待办、辅助整理面经；修改记录遵守现有权限与用户明确指令，不能由推断自动判通过或拒绝。

**第三期：可选连接。** 按实际需求再提供飞书同步、系统/消息提醒；要处理授权、冲突和删除方向，用户必须能选择连接与范围。不把它们作为安装或使用首版的门槛，不承诺本机关闭后继续发送。

首版验收重点为一条完整用户流程和数据保全：

- 同公司两岗位分别管理；手动新增无需公共岗位；打开官网不改变投递状态。
- 从准备、投递到笔试、一面、二面、HR、加面与改期，时间和结果保持独立；未知不补造，真实面试和模拟面试不混用。
- 岗位刷新/下线、简历改名或移除后，个人状态和已保存面经不丢；简历原件已删除时说明不可用，不偷偷保留副本。
- 全量超过一页、当前筛选、勾选记录的导出行数正确；长中文职位描述、多行面经、空薪资与公式样式文本不丢失、不执行，分段能还原。
- 重启后数据和视图保留，写入冲突明确处理；跨账号读写/导出均隔离；密钥、会话令牌和他人数据不得进入文件或公共快照。

首版闭环已通过本地验收：岗位加入、表格编辑、逐轮面试与面经、真实Excel下载和重启保留。下一最小任务是用户在本地预览记录自己的申请并检查导出；看板、日历与外部同步留待后续。
