# 岗位与简历证据匹配闭环设计

## 目标

打通 OpenCareer 当前彼此独立的岗位雷达和多简历库，让用户能够从一个真实岗位出发，选择一份或多份已确认简历，查看可追溯的要求证据矩阵，比较哪份简历更适合，并通过 Career Agent 生成 Markdown 申请准备包。

本阶段回答的是“现有简历中有哪些已确认事实可以佐证这条岗位要求”，不是预测录用概率，也不是判断用户真实能力上限。

## 产品原则

1. 每个匹配结论必须同时回指岗位要求原文和简历中的已确认证据。
2. 没有找到证据只能表示“暂无已确认佐证”，不得表达为“用户不会”。
3. 不输出总匹配百分比，避免将不完整文本包装成精确概率。
4. 不使用手机号、邮箱、出生日期等敏感字段参与匹配或排序。
5. GUI 浏览复用 Career HTTP API；MCP 只服务 Agent 工具调用和交付物生成。
6. 不复制候选人事实。每份简历继续引用自己的已确认文档，共享求职档案继续作为 Agent 的真实事实库。

## 方案选择

### 不采用：模型直接评分

模型直接阅读 JD 和简历虽然开发快，但难以保证同一输入得到稳定结果，也容易把语义相似误写为用户具备某项能力。

### 不采用：纯关键词百分比

纯关键词可以复现，但一个百分比分数会掩盖岗位要求权重、中文表达差异和证据质量，容易产生虚假精度。

### 采用：确定性证据矩阵 + Agent 受约束解释

Career Domain Service 负责要求分类、证据定位、结果持久化、过期判断和多简历排序。Career Agent 只能解释 Service 已返回的岗位事实和简历证据，并生成 Markdown，不得增加新的经历或匹配事实。

## 核心用户流程

1. 用户在岗位详情点击“匹配简历”。
2. 弹窗列出所有未删除的已确认简历，显示简历名称和目标岗位标签。
3. 用户选择 1–5 份简历并开始分析。
4. 页面展示每条岗位要求的类别、证据状态、简历章节和证据原文。
5. 选择多份简历时，页面额外展示横向比较和推荐使用顺序。
6. 用户可点击“生成申请准备包”，进入 Career Agent 对话。
7. Agent 通过 Career MCP 读取同一份证据结果，并在 `artifacts/application-packets/` 生成 Markdown。

## 证据模型

### 岗位要求类别

每条 `requirements` 原文只进行保守的确定性分类：

- `hard`：显式包含“必须、要求、至少、熟练、精通、must、required”等强约束词。
- `preferred`：显式包含“优先、加分、preferred、plus、bonus”等偏好词。
- `unspecified`：无法可靠判断强弱的其他要求。

分类不改写原始要求，也不从职位职责推导隐藏要求。若岗位没有结构化 `requirements`，返回 `INSUFFICIENT_JOB_DATA`，GUI 提示当前 JD 不足以进行证据匹配。

### 简历证据范围

只读取所选简历 `confirmed_sections` 中的：

- 教育经历。
- 工作经历。
- 项目经历。
- 技能。
- 基本信息中的非敏感职业摘要。

明确排除：

- 手机号、邮箱、出生日期和其他联系信息。
- 未确认 preview。
- 已删除简历。
- 模型补写或用户尚未确认的内容。

每条证据包含：

```json
{
  "section": "project",
  "path": "project[0].highlights[1]",
  "excerpt": "基于 LightRAG 构建供应链知识图谱检索",
  "matched_terms": ["RAG", "知识图谱"]
}
```

`path` 是文档内稳定的 JSON 路径描述，不是数据库路径或磁盘路径。

### 证据状态

- `direct`：要求提取出的全部关键术语出现在同一条已确认事实中，或要求中的单一技术术语与 Skill 名称经别名归一化后完全相等。
- `related`：一条已确认事实至少命中一个、但没有命中该要求的全部关键术语。
- `none`：没有找到可引用的已确认事实。

GUI 中文分别显示“有直接证据”“有相关证据”“暂无已确认佐证”。任何状态都不得显示为“满足、不满足、录用概率”。

### 术语处理

第一版使用确定性规范化：

- 英文转小写。
- 统一全角/半角空白和常用分隔符。
- 英文技术词使用 `[A-Za-z][A-Za-z0-9+.#-]{1,}` 提取。
- 中文术语只从集中维护的职业关键词表中按最长词优先提取。首版关键词表覆盖大模型、智能体、产品、需求分析、项目管理、数据分析、机器学习、深度学习、自然语言处理、知识图谱、推荐系统、搜索、后端、前端、全栈、算法、本科、硕士和博士。
- 仅维护小型集中别名表，覆盖产品当前明确需要的等价表达，例如 `LLM/大模型`、`Agent/智能体`、`RAG/检索增强生成`。

别名表只表示术语等价，不表示技能包含关系。例如“Python”不能自动推导“后端开发”，“产品经理”不能自动推导“商业化经验”。

要求无法提取任何关键术语时固定返回 `none`，不使用模糊字符串相似度补判。工作年限不根据简历日期自动推导，除非已确认事实原文明确写出对应年限。

## 多简历比较

比较最多 5 份简历。每份简历展示：

- 硬性要求的直接证据数量。
- 全部要求的直接证据数量。
- 相关证据数量。
- 暂无佐证数量。
- 简历目标岗位标签与岗位标题的确定性术语重合。

推荐顺序使用以下稳定优先级：

1. 硬性要求直接证据更多。
2. 全部直接证据更多。
3. 相关证据更多。
4. 目标岗位标签与标题有重合。
5. 仍相同则明确并列，不使用文件时间或简历名称打破业务并列。

页面只表达“这份简历包含更多可引用证据”，不表达候选人能力高低。

## 数据模型

Career 数据库升级到 schema v6，新增 `job_resume_matches`：

```sql
CREATE TABLE job_resume_matches (
    id TEXT PRIMARY KEY,
    job_id TEXT NOT NULL REFERENCES jobs(id),
    resume_import_id TEXT NOT NULL REFERENCES resume_imports(id),
    job_content_hash TEXT NOT NULL,
    resume_revision_at TEXT NOT NULL,
    result_json TEXT NOT NULL,
    created_at TEXT NOT NULL,
    UNIQUE(
        job_id,
        resume_import_id,
        job_content_hash,
        resume_revision_at
    )
);
CREATE INDEX job_resume_matches_job
    ON job_resume_matches(job_id, created_at DESC);
```

每行是一份岗位版本与一份简历版本的匹配快照。重复分析同一输入复用原结果，保证幂等；岗位或简历变化时生成新快照，旧快照保留审计。

软删除简历时不级联删除历史匹配快照，但正常列表和新分析不再返回该简历。全量删除求职档案时删除所有匹配快照。

## 过期规则

读取匹配结果时比较：

- 当前岗位 `content_hash` 与快照 `job_content_hash`。
- 当前 `resume_imports.updated_at` 与快照 `resume_revision_at`。这里使用 import 修订时间，不使用页面当前由 preview 提供的展示更新时间。
- 当前简历是否已删除。

返回：

- `fresh`：岗位和简历均未变化。
- `stale_job`：岗位 JD 已变化。
- `stale_resume`：简历内容、名称或目标岗位标签已变化。
- `unavailable_resume`：简历已删除。

过期结果可以查看，但 GUI 必须显示“内容已变化，请重新分析”，不得把旧结果当成当前结论。

## Domain 与 Service 边界

新增 `extensions/career_mcp/domain/matching.py`：

- 要求分类。
- 术语规范化和别名展开。
- 从已确认简历生成非敏感证据条目。
- 单条要求与证据的状态判断。
- 多简历稳定排序。

这些函数是无数据库、无网络、无模型调用的纯函数。

新增 `MatchService`：

- 通过 `JobRepository` 读取岗位。
- 通过 `ResumeRepository` 读取所选已确认简历。
- 调用纯函数生成结果。
- 通过独立 `MatchRepository` 持久化或复用快照。
- 计算 fresh/stale 状态。

Adapter、Crawler、Agent Loop 和 GUI 不参与匹配算法。

## HTTP API

### 分析岗位与简历

`POST /v1/career/jobs/{job_id}/matches`

请求：

```json
{
  "resume_ids": ["resume-1", "resume-2"]
}
```

约束：

- 1–5 个不同简历 ID。
- 岗位必须存在。
- 简历必须已确认且未删除。
- 不接受路径、上传 token 或自由格式简历正文。

响应包含岗位快照、每份简历的证据矩阵、比较摘要、推荐顺序和快照状态。

### 读取最近结果

`GET /v1/career/jobs/{job_id}/matches`

返回当前用户本地库中该岗位最近的可用匹配快照，并标明 fresh/stale。没有结果时返回空列表，不自动计算。

页面 API 直接调用 `MatchService`，不经过 MCP、审批或模型。

## MCP 工具

新增：

```text
match_job_to_profile(job_id, resume_ids)
```

工具复用 `MatchService`，返回与 HTTP API 相同的证据矩阵和快照 ID。错误使用稳定代码：

- `JOB_NOT_FOUND`
- `RESUME_NOT_FOUND`
- `INVALID_INPUT`
- `INSUFFICIENT_JOB_DATA`
- `PERSISTENCE_ERROR`

工具不返回手机号、邮箱、原文件、private path、upload token 或未确认内容。

## Career Skill 与申请准备包

更新 `career-application-packet`：

1. 调用 `get_candidate_profile`，确认共享真实事实库存在。
2. 调用 `match_job_to_profile` 获取指定岗位和简历的证据矩阵。
3. 不自行重新评分，不从对话记忆补充经历。
4. 将材料写入：

```text
artifacts/application-packets/<company>-<job>-<date>.md
```

固定章节：

```text
# 申请准备包
## 岗位与官方来源
## 使用的简历
## 岗位要求证据矩阵
## 建议重点强调的已确认经历
## 暂无佐证与待确认问题
## 简历调整建议
## 面试准备问题
## 数据版本与生成时间
```

“简历调整建议”只能建议调整顺序、强调已有事实或补充用户确认，不得生成虚构项目、指标、头衔或技能。

## GUI

岗位详情头部在“查看官网”旁增加“匹配简历”。

### 简历选择弹窗

- 列出简历名称、格式、目标岗位标签和更新时间。
- 默认不自动选择，用户显式选择 1–5 份。
- 选中已删除或过期 ID 时以后端结果为准并显示中文错误。

### 单简历结果

- 顶部显示简历名称、快照时间和 fresh/stale 状态。
- 按硬性要求、优先项、未分类要求分组。
- 每条要求显示状态、证据章节、原文摘录和命中术语。
- `none` 状态固定显示“暂无已确认佐证”，不生成负面评价。

### 多简历结果

- 先显示横向摘要，再允许展开每份简历的完整证据矩阵。
- 推荐项显示“可引用证据更充分”，同时列出稳定排序理由。
- 并列时不强行选出唯一简历。

### 生成申请准备包

按钮将 `job_id`、`resume_ids` 和匹配快照 ID 作为不透明标识加入 Career 对话，由 Agent 调用 MCP 并通过既有工作区写文件流程生成 Markdown。GUI 不直接写 artifact。

## 错误与空状态

- 没有简历：引导“前往我的求职档案导入简历”。
- 没有已确认章节：该简历不允许参与匹配。
- 岗位无结构化要求：显示“当前 JD 缺少可分析的职位要求”，仍允许查看原 JD。
- 岗位已下线：允许分析，但显示醒目的“岗位已下线”提示。
- 匹配结果过期：允许查看并提供“重新分析”。
- 单份分析失败不应返回其他简历的部分成功结果，整个请求保持原子语义。

## 测试与验收

### Domain

- 要求分类覆盖 hard、preferred、unspecified。
- direct、related、none 均有最小正反例。
- 敏感字段永不进入证据语料。
- 别名只做等价映射，不做能力推导。
- 多简历排序稳定，完全相同结果明确并列。

### Repository 与 Service

- schema v5 可无损迁移到 v6。
- 同一岗位 hash 与简历更新时间重复分析幂等。
- 岗位变化和简历变化分别产生新快照并标记旧结果过期。
- 已删除简历不能新建匹配，但历史快照外键完整。
- 全量删除求职档案同步删除匹配快照。

### HTTP 与 MCP

- 1 份和 2–5 份简历成功。
- 空列表、重复 ID、超过 5 份、缺失岗位、缺失简历使用稳定错误。
- HTTP 与 MCP 返回相同领域结果。
- 响应不包含敏感字段和私人路径。

### GUI

- 从岗位详情打开简历选择。
- 单简历证据矩阵展示。
- 多简历比较、推荐和并列展示。
- stale 提示和重新分析。
- 无简历、无要求、已下线岗位中文空状态。
- 生成申请准备包只准备 Agent 请求，不直接写文件。

### 端到端

- 使用真实岗位和真实简历进行只读匹配。
- 生成一份真实 Markdown 申请准备包。
- 人工检查每条引用都能追溯到岗位原文或已确认简历事实。
- 后端、GUI、production build、`git diff --check` 全部通过。

## 阶段门与停止条件

### Gate 0：基线固化

先整理并提交当前已完成改动，重跑现有后端 227、GUI 150 和 production build。基线不绿时不开始 schema v6。

### Gate 1：最低交付

单岗位、单简历、证据矩阵通过 Domain、Service、HTTP 和 GUI。此 Gate 未通过时不做多简历比较。

### Gate 2：标准交付

多简历比较、稳定推荐、快照持久化和过期检测通过。此 Gate 未通过时不接 Agent 交付物。

### Gate 3：冲刺交付

Career MCP、Skill 和 Markdown 申请准备包端到端通过。

## 明确不做

- 录用概率或总匹配百分比。
- 向量数据库、Embedding 或复杂推荐模型。
- 自动改写或覆盖用户简历文件。
- 自动投递、招聘网站登录或验证码处理。
- 岗位收藏和申请状态跟踪。
- 基于敏感字段的筛选或排序。
- 继续扩展招聘公司 Adapter。
