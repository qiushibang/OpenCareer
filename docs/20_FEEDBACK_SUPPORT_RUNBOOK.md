# 用户反馈、脱敏诊断与问题中心

本版本三阶段代码已于 2026-09-20 发布生产，并为用户确认的账号配置一名管理员。
主机定时检查和外部消息提醒仍是独立步骤，当前均未启用；管理员主动打开问题中心
查看。不能把代码上线等同于真人多账号、容量或异地可用性验收已完成。

## 用户和管理员如何使用

用户从侧栏或手机页面的“帮助与反馈”提交功能故障、建议或其他问题；报错
旁也有反馈入口。只自动关联服务器确认属于当前账号的排查编号，不上传对话、
输入、完整简历、控制台、录屏或截图。失败保留草稿；“我的反馈”查看状态和回复。
登录前可提交匿名反馈，但不绑定账号，也不能在账号中追踪回复。

管理员仍使用原来的登录流程。服务端 `OPENCAR_SUPPORT_ADMIN_IDS` 指定应用用户
编号（不是邮箱或客户端参数），默认空，即无人拥有管理权限。管理员“问题中心”
可以筛选、回复、改状态和合并重复问题；只访问支持数据，不能因此访问用户简历、
对话、文件或 Shell（命令执行环境）。合并保持单层，不向用户展示另一条反馈正文
或编号。管理操作有不含正文的审计记录。

反馈文字可能是恶意内容：按纯文本展示，不交给 Agent 执行，不信任其指令，也
不自动打开链接。用户主动输入的反馈本身仍可能含私密内容，因此管理访问应最少。

## 存储和数据边界

云端仅使用现有 PostgreSQL，不静默降级成本地数据库。迁移 11–18 新增支持表、
强制 Row-Level Security（行级安全隔离）和窄范围管理策略；匿名入口仅有受控
查询及插入策略，没有匿名更新或删除策略。管理员上下文是事务局部的，连接复用
后不残留。桌面端使用独立 `support.db`，故障不阻止原业务启动。

诊断仅保存编号、固定错误与页面类别、时间、状态、耗时、来源和受控发布版本。
不保存任意异常文本、模型原始错误、请求网址、查询串、密钥、Cookie（会话凭证）
或私密正文。云端运行日志也仅输出固定级别和组件类别，无访问日志和堆栈正文。
这会减少详细定位信息：先用编号、类别、版本和时间复现，不临时开启私密日志。

每用户诊断最多 1000 条、保存 14 天；审计最多 10000 条、保存 30 天。反馈每账号
最多 500 条，匿名入口总计最多 500 条；达到上限会拒绝新增而不是删除用户反馈。
初版匿名入口使用全局限频以避免伪造转发地址绕过，可能被滥用耗尽；公开推广前
宜配合可信入口限频，观察容量并人工处理，不把限频等同于完整抗攻击方案。
所有新增支持写请求最多 8192 字节，用户及管理员字段严格验证。

## 生产发布顺序

1. 按文档 18 创建 PostgreSQL 恢复点、验证隔离恢复并保留旧镜像；不要删除数据卷。
2. 用户确认管理员身份后，核实其实际应用用户编号，再设置服务端管理员白名单。
   不授予 Agent 管理工具或数据库凭证，不给普通用户数据库连接能力。
3. 构建与后端配置使用相同 `OPENCAR_RELEASE`；前端构建会将其传入
   `VITE_OPENCAR_RELEASE`。允许安全版本标识字符，缺失或不匹配显示 unknown，
   不从客户端保存任意版本文本。域名版编排已预留发布版本及管理员环境变量。
4. 在候选实例应用新增迁移并检查健康；迁移后的数据库回滚必须恢复备份，不能
   只换旧镜像就宣称支持数据完整。前后端作为配套版本验收后发布。
5. 真实浏览器验收普通账号、另一账号和指定管理员，登录前出口及手机页面。
   检查隔离、回复同步、权限拒绝、编号与隐私；再逐步扩大公开范围。

## 独立主机检查（默认不开启，不外发）

入口：`python -m extensions.support.watchdog`。它独立于主应用进程，只检查本机
健康端点、磁盘、Linux 内存及可选容器重启指标；无公共写接口或 Agent 工具。
单次网络及系统检查有超时。数据库不可用时保存有界固定类别，恢复后再记入支持
告警；测量失败不视为故障恢复。默认不发送飞书、邮件或其他外部通知。

`deploy/opencareer-watchdog.service` 和 `.timer` 是安装模板，截至 2026-09-20
仍未在生产安装或启用。运维人员需准备独立目录 `/opt/opencareer-monitor`（同一已审查源码及
项目现有运行依赖，不需要 OCR），独立只读代码虚拟环境与无登录的
`opencareer-monitor` 系统账号；仅状态目录允许写入。不可让该任务依赖
`docker exec` 主应用，否则主应用停机时也无法检查。

`/etc/opencareer-watchdog.env` 由运维创建，root 所有、权限 600，不进仓库，内容：

```text
DATABASE_URL=<受控应用数据库连接，不使用超级用户>
OPENCAR_SUPPORT_ADMIN_IDS=<经确认的应用管理员编号>
OPENCAR_SUPPORT_WATCHDOG_ADMIN_ID=<上述允许的编号>
OPENCAR_WATCHDOG_HEALTH_URL=http://127.0.0.1:18768/v1/health
OPENCAR_WATCHDOG_DISK_PATH=/opt
OPENCAR_WATCHDOG_MEMINFO_PATH=/proc/meminfo
```

健康目标仅允许固定本机地址、固定 `/v1/health`，禁代理和重定向。端口和磁盘
路径按实际部署确认，不能盲用示例。先运行 `--dry-run`：只读检查、不连数据库、
不写状态，然后手动跑一次普通检查，确认状态和权限，再安装并开启定时器。

默认不授予监控账号 Docker（容器运行管理）访问，因此“重启指标不可用”正常；
若确需重启检查，由运维另行评估最小授权并设置固定
`OPENCAR_WATCHDOG_CONTAINER`，不能把 Docker socket（管理接口）给 Agent 或用户。
维护期间可设置 `OPENCAR_WATCHDOG_MAINTENANCE=1` 抑制计划重启提醒。

内存/磁盘使用率达到 90% 提醒；15 分钟内同类应用错误达到 10 条提醒。浏览器
报告可被用户伪造，只作排查信号。固定类别去重，同一活动告警 15 分钟内只产生
一次通知事件。事件只含编号、类别和数量，目前仅写本机结果与站内问题中心。
查看定时器是否运行及其日志，不能只看站内页面；数据库同时故障时站内也不可见。
这不替代异地可用性监控，尚无外部渠道推送；目的地须用户确认后另行接入。
